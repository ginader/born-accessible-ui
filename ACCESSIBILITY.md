# Accessibility

**Born-Accessible UI** is an open-source Agent Skill, prompt protocol set, and automated verification toolkit that teaches AI coding agents to build web interfaces targeting **WCAG 2.2 Level AA** on the first pass. This does not remove the need for manual testing: once every automatically found issue is fixed, you still need to test the result with a keyboard, a screen reader, and the other manual checks listed under [Known limitations](#known-limitations-what-automated-checks-cannot-tell-you).

GitHub surfaces this `ACCESSIBILITY.md` file in the repository's **Accessibility** tab. It documents the accessibility status of the files in this repository, what our verification scripts check (and what still requires a human), and how to report accessibility barriers.

## Conformance target & standards

The protocols, reference examples, and HTML report template in this repository target:

- **[Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/) Level A and Level AA**
- **[W3C First Rule of ARIA](https://www.w3.org/TR/using-aria/#rule1)** and the **[ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/)**

Specifically, the kit enforces three protocols during UI generation and review:

1. **Protocol 1 — Silent Reasoning (`A11Y-PLAN`)**: Landmarks (`<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>`), a single `<h1>` and unskipped heading hierarchy, native interactive controls, keyboard behavior, and color contrast pairs are planned before writing markup.
2. **Protocol 2 — Color Safety**: Every foreground token in `:root` carries a computed WCAG 2 contrast assertion (`/* Contrast: X.X:1 vs #bg (AA|AAA|UI) */`) verified mathematically by `scripts/lint.mjs` (`>= 4.5:1` for normal text, `>= 3.0:1` for large text and UI components).
3. **Protocol 3 — First Rule of ARIA**: Native HTML elements (`<button>`, `<a href>`, `<dialog>`, `<details>`/`<summary>`, `<input type="checkbox" role="switch">`, `<label for>`) are used instead of repurposed `<div>` or `<span>` elements, paired with visible `:focus-visible` indicators, `24×24 CSS px` minimum target sizes, `320 CSS px` reflow, and `prefers-reduced-motion` support.

## Known limitations (what automated checks cannot tell you)

A core principle of this project is that **zero automated violations is a baseline, never a claim of full WCAG conformance.**

`scripts/audit.mjs` (Playwright + `axe-core` across initial and hidden states, plus `320 CSS px` reflow and placeholder-only label checks) and `scripts/lint.mjs` (computed contrast assertion verification and static anti-pattern checks) catch many structural and contrast defects, but automated tools cannot evaluate every success criterion. Always pair this kit with manual checks:

- **Keyboard walk-through**: Verify `Tab`, `Shift+Tab`, `Enter`, `Space`, `Escape`, and arrow-key navigation across all interactive controls, modals, and composite widgets, confirming logical focus order and no keyboard traps.
- **Visible focus indicators**: Confirm that every interactive element displays a clear `:focus-visible` indicator against its surrounding surface.
- **Screen reader testing**: Spot-check names, roles, states, announcements, and dynamic updates with a screen reader (such as VoiceOver, NVDA, JAWS, Orca, or TalkBack).
- **"Needs review" items**: Inspect items flagged as `review` by `axe-core` (for example, text over gradients, images, translucent surfaces, or overlapping layers in modal dialogs).
- **Zoom & reflow usability**: Verify that the interface remains usable and readable at `200%` browser zoom and `320 CSS px` viewport width (`400%` zoom).
- **Content quality**: Check that image `alt` text, link text, headings, form labels, and error recovery instructions are meaningful to humans.

## Verify this repository locally

You can run the kit's static linter and browser audit on the repository's own reference example and generated report:

```bash
# 1. Verify contrast assertions and static HTML/CSS rules on the Born-Accessible example
node born-accessible-ui/scripts/lint.mjs examples/after-born-accessible.html

# 2. Run the full Playwright + axe-core + 320px reflow audit on the Born-Accessible example
node born-accessible-ui/scripts/audit.mjs examples/after-born-accessible.html

# 3. Audit the generated HTML report itself
node born-accessible-ui/scripts/audit.mjs a11y-report/report.html --out a11y-report/self-check
```

## Reporting accessibility barriers

If you run into an accessibility barrier anywhere in this repository (the documentation, the reference example, the generated HTML report, or the CLI output), please [open an issue](https://github.com/ginader/born-accessible-ui/issues/new) and include:

- The file, page, or command where you hit the barrier
- What you expected to happen, and what happened instead
- Your browser and operating system, plus any assistive technology you use (for example a screen reader, screen magnifier, voice control, or keyboard-only navigation), with versions if you know them
- Steps to reproduce, and a screenshot or recording if it helps

Issues are public, so only include details you're comfortable sharing.

[`examples/before-unguided.html`](examples/before-unguided.html) is inaccessible on purpose, so please don't report its failures as barriers.
